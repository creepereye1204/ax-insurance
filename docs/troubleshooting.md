## 1. 상품이 하나뿐인데 에이전트가 상품명을 되물음

**증상**
"통원 치료비 5만원 나왔으면 얼마 받아?" 질문에 도구를 한 번도 호출하지 않고 "어떤 상품인지 알려주세요"라고만 답함. 등록된 상품은 1개뿐이었다.

**원인 분석**
실행 로그(`agent_runs.trace`)를 보니 도구 호출이 0건. 시스템 프롬프트에 "상품이 명시되지 않았을 때 어떻게 할지" 규칙이 없어서, 모델이 안전하게 되묻는 쪽을 택했다.

**해결**
시스템 프롬프트에 행동 규칙 추가:
- 상품명이 없으면 되묻기 전에 `list_products` 로 확인, 하나뿐이면 그 상품 기준으로 답변
- 금액 계산이 필요하면 비율·공제금액·한도를 적용한 계산 과정 제시

**결과**
같은 질문에 `list_products → search_policy` 순으로 도구를 호출하고, "50,000 − 10,000 = 40,000원, 한도 20만원 이내" 계산 과정과 근거 조항(제3조)을 함께 답변.

**배운 점**
에이전트 실패는 "모델이 멍청해서"가 아니라 대부분 지시가 비어 있어서 생긴다. 도구 호출 기록을 남겨두지 않았다면 원인을 추측만 했을 것이다. → 이후 Eval 셋에 이 질문을 회귀 테스트로 포함.

## 2. Spring → FastAPI 호출 시 요청 본문 유실 (422)

**증상**
기간계(Spring)가 청구 접수 후 AI 서비스(FastAPI) `/chat` 을 호출하면 `422 Unprocessable Entity — body: Field required`. curl 로 같은 JSON 을 보내면 정상.

**원인 분석**
- 같은 요청이 curl 에선 되고 Java 에서만 실패 → 클라이언트 차이
- `RestClient` 에 `JdkClientHttpRequestFactory` 를 사용 중. JDK `HttpClient` 는 기본 버전이 **HTTP/2** 라서, 평문 http 에서 `Upgrade: h2c` 헤더로 업그레이드를 시도한다
- uvicorn 은 h2c 업그레이드를 지원하지 않고, 업그레이드 요청의 본문이 애플리케이션까지 전달되지 않아 본문이 비어 있는 것으로 처리됨

**해결**
```java
HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_1_1)   // h2c 업그레이드 방지
        .connectTimeout(props.connectTimeout())
        .build();
```

**결과**
AI 검토 정상 동작 (청구 → `AI_REVIEWED`).
장애 중에도 청구는 설계대로 `MANUAL_REVIEW`(수동심사)로 전환되어 **기간계 업무는 멈추지 않았다** — 장애 격리 설계가 실제로 검증된 사례.

**배운 점**
라이브러리 기본값(HTTP 버전, 타임아웃, 커넥션 풀)은 서버 쪽과 맞는지 확인해야 한다. 이종 시스템 연계에서는 "프로토콜 버전"도 계약의 일부다.

## 3. 공유 프록시 기본 타임아웃(50초)과 LLM 응답 시간 충돌

**증상 (배포 전 예방)**
로컬 LLM 응답이 보통 20~45초, 모델 콜드 스타트 시 60초 이상. 공유 HAProxy 의 기본 `timeout server` 는 50초 → 느린 요청은 504 가 날 상황.

**원인 분석**
HAProxy 는 여러 팀 서비스가 같이 쓰는 공유 인프라. 전역 `defaults` 를 바꾸면 다른 서비스에도 영향이 간다.

**해결**
- 전역 설정은 건드리지 않고 **우리 백엔드 블록에만** `timeout server 3m` 추가 (기존 다른 서비스의 선례와 같은 방식)
- 적용 전: 설정 백업 → 실행 중인 HAProxy 컨테이너 안에서 `haproxy -c` 로 문법 검증 → 통과 후 재기동
- 적용 전후로 다른 서비스 6개 도메인 응답 코드를 비교해 영향 없음 확인

**배운 점**
공유 인프라 변경은 "내 서비스가 되는지"보다 "남의 서비스가 안 깨졌는지"를 먼저 확인해야 한다. 변경 범위를 최소화하고, 백업·검증·비교를 습관화.

## 4. IP별 요청 제한이 전체 제한으로 동작할 뻔함

**증상 (배포 중 발견)**
게이트웨이(nginx)에 LLM 호출을 IP당 분당 6회로 제한했는데, HAProxy 설정을 확인해 보니 `X-Forwarded-For` 를 넘겨주지 않고 있었다.

**원인 분석**
nginx 입장에서는 모든 요청이 HAProxy 컨테이너 IP 에서 온다 → "IP당 6회"가 사실상 **전체 사용자 합계 6회**로 동작.

**해결**
- HAProxy 우리 백엔드 블록에 `option forwardfor` 추가
- nginx 는 도커 사설 대역에서 온 `X-Forwarded-For` 만 신뢰 (`set_real_ip_from 172.16.0.0/12` 등). 아무 대역이나 신뢰하면 클라이언트가 헤더를 위조해 제한을 우회할 수 있다

**결과**
게이트웨이 접근 로그에 실제 클라이언트 IP 가 기록되는 것 확인.

**배운 점**
리버스 프록시가 여러 단이면 "클라이언트 IP"가 무엇인지부터 확인해야 한다. 요청 제한·로그·감사 기록이 모두 이 값에 의존한다.

## 5. nginx 설정을 고쳤는데 반영되지 않음 (파일 bind mount)

**증상**
게이트웨이 `nginx.conf` 에 새 API 경로를 열고 `nginx -t` → `nginx -s reload` 까지 했는데 `/core/customers` 가 계속 404. 문법 검사도 통과했다.

**원인 분석**
- 컨테이너 안의 설정 파일 내용을 확인해 보니 **수정 전 내용** 그대로
- `stat -c %i` 로 inode 를 비교: 호스트 `21636685`, 컨테이너 `21636592` — 서로 다른 파일
- `docker-compose.yml` 에서 **디렉토리가 아니라 파일 하나**를 bind mount 하고 있었다. 편집기가 저장할 때 기존 파일을 덮어쓰지 않고 새 파일로 교체(rename)하면 inode 가 바뀌고, 컨테이너는 계속 옛 inode 를 본다

**해결**
- `docker compose up -d --force-recreate gateway` 로 컨테이너를 다시 만들어 새 파일을 마운트
- 컨테이너를 재생성하면 IP 가 바뀔 수 있으므로 공유 HAProxy 재시작 (배포 규칙 R21)
- 같은 이유로 nginx 도 업스트림(`api`, `core`) 주소를 시작 시 한 번만 해석한다는 점을 확인하고, `resolver 127.0.0.11` + 변수 업스트림으로 바꿔 **기간계·AI 컨테이너가 재생성돼도 게이트웨이가 따라가도록** 예방

**배운 점**
"reload 했는데 안 바뀐다"면 설정 내용이 아니라 **컨테이너가 보고 있는 파일이 맞는지**부터 확인한다. 자주 바뀌는 설정은 파일 단위보다 디렉토리 단위로 마운트하는 편이 안전하다.

## 6. 고객 검색이 아무 반응 없음 — 요청 제한과 삼켜진 오류

**증상**
브라우저 자동 테스트(Playwright)에서 고객 검색 결과가 나타나지 않아 30초 타임아웃. 화면에도 아무 메시지가 없었다.

**원인 분석**
- 게이트웨이의 일반 API 요청 제한이 **IP당 분당 60회**였다. 화면 하나를 열 때 여러 API 를 호출하고, 검색은 타이핑할 때마다 호출하므로 실제 사용 패턴에서 쉽게 넘는다 → 429 응답
- 검색 컴포넌트가 `fetch` 오류를 처리하지 않아 **실패가 화면에 드러나지 않았다**

**해결**
- 일반 API 제한을 초당 10회(버스트 50)로 현실화. 공용 GPU 를 쓰는 LLM 호출 제한(분당 6회, 동시 2건)은 그대로 유지
- 검색 실패 시 오류 메시지를 결과 영역에 표시

**배운 점**
요청 제한 값은 "보호"만 보고 정하면 정상 사용을 막는다. 화면 한 번에 몇 번 호출하는지부터 세어 봐야 한다. 그리고 실패를 삼키는 UI 는 장애 원인을 감춘다.

## 7. 빠르게 이동하면 이전 화면이 현재 화면을 덮어씀 (경쟁 상태)

**증상**
자동 테스트에서 메뉴를 빠르게 연속 이동하면 간헐적으로 현재 화면 제목(h1)을 찾지 못함. 각 화면을 따로 열면 정상, API 응답도 정상(0.01~0.06초).

**원인 분석**
SPA 라우터가 화면 함수를 `async` 로 실행하는데, 이전 화면의 API 응답이 늦게 도착하면 그 함수가 **공용 `view` 요소에 렌더링**해 이미 바뀐 현재 화면을 덮어쓸 수 있다.

**해결**
- 라우팅할 때마다 새 컨테이너를 만들어 붙이고, 각 화면 함수는 **시작 시점의 컨테이너를 지역 변수로 잡아** 그곳에만 렌더링
- 늦게 도착한 이전 화면의 렌더링은 화면에서 떨어진(버려진) 컨테이너에 쓰여 영향이 없다

**결과**
전체 화면 흐름 테스트(설계 → 설계서 → 고지 → 청약서 → 서명 → 계약 → 청약철회 → 청구) 연속 2회 통과, 콘솔 오류 0건.

**배운 점**
비동기 렌더링에서는 "응답이 도착했을 때 그 화면이 아직 유효한가"를 항상 따져야 한다. 테스트가 간헐적으로 실패하면 테스트 탓으로 돌리기 전에 경쟁 상태를 의심한다.
